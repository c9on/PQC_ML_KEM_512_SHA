# ML-KEM-512 algorithm and RTL mapping walkthrough

## 1. Cryptography background: a lattice

A lattice is a regular grid of points made from integer combinations of basis vectors. For a simple two-dimensional lattice, points might be generated by:

$$
\mathcal L=\{x b_1+y b_2\mid x,y\in\mathbb Z\}.
$$

Some lattice problems are easy to solve when the basis vectors are short and nearly perpendicular, but become hard when the published basis is large, skewed, or noisy. Lattice cryptography hides secret information using a hard lattice-style equation plus a small error term.

ML-KEM uses a **module** version of Learning With Errors (Module-LWE). “Module” means the scalar elements of ordinary LWE are replaced by polynomials. This combines efficient polynomial arithmetic with a structured hard problem.

### Closest-vector intuition

Imagine that the correct lattice point is $(10,20)$. An attacker is shown a noisy public point $(10,20)+e$, where $e$ is tiny. With an ordinary good lattice basis, finding the nearest exact point may be easy. With the carefully structured public basis and high dimensions used in a cryptographic system, recovering the secret basis/coefficient information is assumed to be computationally hard.

ML-KEM does not directly encode the “picture” of a lattice in RTL. Instead, the hardware performs the algebraic equations whose security is related to that hard problem.

## 2. Why a KEM instead of ordinary encryption

A public-key encryption scheme (PKE) encrypts a message with a public key. A key encapsulation mechanism (KEM) establishes a shared symmetric key and gives the sender a ciphertext.

ML-KEM is internally constructed from:

```text
PKE key generation
+ PKE encryption
+ PKE decryption
+ hashing and ciphertext re-encryption
= ML-KEM KEM
```

The PKE is the mathematical core. The hash and re-encryption layer converts it into a KEM with implicit rejection and binds the shared secret to the ciphertext.

## 3. The working mathematical ring

Each coefficient is an integer modulo:

$$q=3329.$$

Each polynomial has 256 coefficients and multiplication follows:

$$x^{256}=-1.$$

Thus the ring is

$$R_q=\mathbb Z_q[x]/(x^{256}+1).$$

For example, if a product produces $x^{256}$, the RTL treats it as $-1$. This sign change is why direct convolution has a negative wrapped section and why ML-KEM uses a negacyclic NTT.

In RTL, a 3072-bit value stores 256 coefficients of 12 bits each:

$$256\times12=3072\text{ bits}=384\text{ bytes}.$$

## 4. Public matrix, secret, and public value

ML-KEM-512 sets $k=2$. Key generation samples a matrix and vectors:

$$
A=\begin{bmatrix}A_{00}&A_{01}\\A_{10}&A_{11}\end{bmatrix},
\qquad
s=\begin{bmatrix}s_0\\s_1\end{bmatrix},
\qquad
e=\begin{bmatrix}e_0\\e_1\end{bmatrix}.
$$

It computes:

$$
t=A s+e\pmod q.
$$

Expanded by row:

$$t_0=A_{00}s_0+A_{01}s_1+e_0,$$

$$t_1=A_{10}s_0+A_{11}s_1+e_1.$$

The public key contains $t_0,t_1,\rho$. The secret key contains the transformed secret $\widehat{s}$, the public key, its hash, and $z$.

An observer sees $A$ and $t$, but not $s$ or $e$. Recovering $s$ from the noisy system is the assumed hard Module-LWE task.

## 5. Seeded deterministic construction

ML-KEM operations are deterministic in their test interface. All apparent pseudorandom material comes from SHAKE streams seeded by cryptographic inputs.

### 5.1 Key-generation seed expansion

Given 32-byte seed $d$:

$$
(\rho,\sigma)=\operatorname{SHA3\text{-}512}(d\,\|\,02_{16}).
$$

- $\rho$ publicly seeds matrix $A$.
- $\sigma$ secretly seeds $s$ and $e$.

The RTL is `sha3_512({dd, 8'h02}, 33)` in `keypair_ek` and `keypair_dk`.

### 5.2 Matrix expansion

Each matrix polynomial is:

$$A_{ij}=\operatorname{SampleNTT}(\operatorname{SHAKE128}(\rho\|j\|i)).$$

Rejection sampling converts groups of 12 bits into coefficients, keeping only values less than 3329.

RTL mapping:

- `matrix_poly` creates bytes `rho || j || i`.
- `shake128` produces the stream.
- `sample_ntt` rejects invalid candidates and stores 256 accepted coefficients.

### 5.3 Secret and error sampling

For nonce values identifying each polynomial:

$$
p=\operatorname{CBD}_\eta(\operatorname{SHAKE256}(\sigma\|nonce)).
$$

CBD takes two groups of $\eta$ bits, sums each group, and subtracts.

RTL mapping:

- `noise` creates `seed || nonce`.
- `shake256` generates bytes.
- `cbd` computes $a-b$ for each of 256 coefficients.

## 6. NTT: why and how

Normal polynomial multiplication takes roughly $256^2$ products. NTT changes a polynomial into a representation where base multiplication is much cheaper:

$$
\widehat a=\operatorname{NTT}(a).
$$

The hardware butterfly transforms pairs:

$$t=\zeta\,a_{j+len}\pmod q,$$

$$a_{j+len}=a_j-t,$$

$$a_j=a_j+t.$$

All results are reduced modulo $q$.

ML-KEM NTT uses 128 quadratic base factors, represented in RTL as 64 four-coefficient groups by `basemul`.

After NTT-domain multiplication:

$$c=\operatorname{INTT}(\widehat a\star\widehat b),$$

where $\star$ is the base-multiply operation.

RTL mapping:

- `ntt`: staged forward butterflies.
- `basemul`: four-coefficient quadratic base multiplication.
- `intt`: reverse butterflies and final multiplication by 3303.

## 7. Key generation, step by step

### Step 1: expand seeds

$$G(d\|2)=(\rho,\sigma).$$

### Step 2: form public matrix

$$A=\operatorname{Expand}(\rho).$$

### Step 3: sample secret and noise

$$s,e\leftarrow\operatorname{CBD}_{3}(\operatorname{SHAKE256}(\sigma\|nonce)).$$

### Step 4: compute public polynomial vector

$$\widehat s=\operatorname{NTT}(s),$$

$$\widehat e=\operatorname{NTT}(e),$$

$$\widehat t=A\widehat s+\widehat e.$$

The implementation serializes $t$ in this NTT-domain representation.

### Step 5: serialize EK

$$EK=\operatorname{Encode}_{12}(\widehat t_0)\|\operatorname{Encode}_{12}(\widehat t_1)\|\rho.$$

Sizes:

$$384+384+32=800\text{ bytes}.$$

### Step 6: assemble DK

$$DK=\operatorname{Encode}_{12}(\widehat s_0)\|
\operatorname{Encode}_{12}(\widehat s_1)\|EK\|H(EK)\|z.$$

RTL mapping: `keypair_ek` generates EK; `keypair_dk` serializes the secret vector and appends EK, hash, and z.

## 8. Encapsulation, step by step

Given EK and 32-byte message $m$:

### Step 1: derive shared key and coins

$$H(EK)=\operatorname{SHA3\text{-}256}(EK),$$

$$(\bar K,coins)=\operatorname{SHA3\text{-}512}(m\|H(EK)).$$

### Step 2: sample encryption quantities

$$r_0,r_1\sim CBD_3,$$

$$e_{1,0},e_{1,1},e_2\sim CBD_2.$$

### Step 3: create ciphertext polynomials

$$u=A^Tr+e_1,$$

$$v=t^Tr+e_2+\operatorname{Encode}(m).$$

The transposed matrix means the first `u` uses row $A_{0,0},A_{1,0}$, and the second `u` uses row $A_{0,1},A_{1,1}$.

### Step 4: why noise permits recovery

The recipient computes $v-s^Tu$. Substituting the equations gives approximately the encoded message plus small noise terms. Because a 0 message maps to 0 and a 1 message maps near $q/2=1664.5$, the recipient can determine the original bit even after small noise and compression.

### Step 5: compress and serialize

$$C=\operatorname{Pack}_{10}(\operatorname{Compress}_{10}(u_0))
\|\operatorname{Pack}_{10}(\operatorname{Compress}_{10}(u_1))
\|\operatorname{Pack}_{4}(\operatorname{Compress}_{4}(v)).$$

Sizes:

$$320+320+128=768\text{ bytes}.$$

RTL mapping: `encrypt_pke` performs every equation and calls `pack10`, `pack4`, and compression helpers.

## 9. Decapsulation, step by step

### Step 1: recover message

Unpack and decompress $C$ into $u_0,u_1,v$.

Compute:

$$w=s^Tu$$

in the NTT domain, invert-transform it, and calculate:

$$m_{poly}=v-w.$$

`decode_msg` maps each coefficient back to one bit.

### Step 2: reproduce encapsulation

Compute:

$$(K',coins')=G(m'\|H(EK)).$$

Run PKE encryption again using $m'$ and $coins'$ to obtain $C'$.

### Step 3: decide shared secret

If every byte matches, $C'=C$, the caller receives $K'$.

If any byte differs, the caller receives:

$$J(z\|C)=\operatorname{SHAKE256}(z\|C).$$

This is implicit rejection: malformed ciphertext does not produce an obvious “decryption failed” secret.

The RTL `ok` flag accumulates all ciphertext-byte comparisons. `status=30` identifies a ciphertext match; `status=34` identifies implicit rejection.

## 10. Mapping the full algorithm to RTL names

| FIPS 203 concept | RTL package helper | Engine call site |
|---|---|---|
| $G(d\|2)$ / $G(m\|H(EK))$ | `sha3_512` | `keypair_ek`, `keypair_dk`, KEM `COMPUTE` |
| $H(EK)$ | `sha3_256` | key validation and KEM operations |
| Matrix expansion | `shake128` + `sample_ntt` | `matrix_poly` |
| CBD noise | `shake256` + `cbd` | `noise` |
| Polynomial multiplication | `ntt`, `basemul`, `intt` | keygen/encrypt/decrypt equations |
| 12-bit serialization | `pack12`, `unpack12` | EK and DK |
| 10/4-bit serialization | `pack10`, `unpack10`, `pack4`, `unpack4` | ciphertext |
| Message mapping | `encode_msg`, `decode_msg` | PKE encrypt/decrypt |
| Implicit rejection | `shake256_32` | decapsulation `kb` result |
| Key checks | `ek_valid`, `dk_valid` | FSM `ACQUIRE` |

## 11. What is algorithmically complete versus hardware-incomplete

The equations above are behaviorally implemented and checked by ACVP/randomized tests. The current `COMPUTE` state still evaluates complete package functions as a large combinational expression. Therefore:

- the mathematical mapping is present;
- simulation functional coverage is present;
- the practical FPGA datapath is not yet iterative or timing-closed;
- security certification and side-channel validation are not present.
